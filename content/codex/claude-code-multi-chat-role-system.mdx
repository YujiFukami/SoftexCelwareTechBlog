1台のPCで<Term>Claude Code</Term>のチャットを20個近く開き、**チャットごとに役割を1つだけ持たせて、チャットどうしが直接やり取りしながら仕事を流す**仕組みを運用しています。利用者は統括のチャットに指示を出し、判断が必要なところだけボタンで答えます。

動画とブログの制作で組み上げた仕組みですが、ソフトウェアの開発にも移せる形で整理します。

ある日の実績では、動画5本（本編とショートで10本）を、題材の選定から制作、品質確認、公開の予約まで進めました。利用者が自分で行ったのは、統括への指示と、品質確認のページでの「直す／直さない」の判断、予約日時のOKだけでした。

## 仕組みの5つの柱

| 柱 | 目的 | 実体 |
|---|---|---|
| 役割と名前 | だれが何をするかを固定する | チャットの名前の先頭の記号と、役割ごとの指示書 |
| 連絡 | 利用者が文を貼って回る手間をなくす | 開いているチャットへの直接送信と、閉じているチャット宛ての受付箱 |
| 権限と関所 | 取り返しのつかない操作を1か所に集める | 利用者のOKが必要な操作の決まりと、命令を止めるフック |
| ルールの共有 | 長く動くチャットが古いルールで動かないようにする | 共通ルールの「変更の記録」と、変更を知らせるフック |
| 引き継ぎ | 会話が要約されても続きから動けるようにする | 役割ごとの引き継ぎメモと、要約の前後に読み直させるフック |

フックは、Claude Codeが決まった場面（チャットの開始時、指示の受信時、命令の実行直前など）で自動的に動かす小さなスクリプトです。

## 役割の分け方

| 役割 | すること | しないこと |
|---|---|---|
| 統括 | 利用者の指示を依頼文にして各役割へ送り、届いた物を自分でも確かめて報告する | 自分で作らない |
| 選定 | 題材の候補を、契約の条件も見て選ぶ | 作らない |
| 品質確認 | 決まった項目で確かめ、報告を書く | 直しを勝手に送らない |
| 予約担当 | 公開日時の案を見せ、OKを取って予約する | **予約はここだけ** |
| 技術検証 | フックや道具を作る | 制作はしない |
| モニター | 初めて見る人の立場で感想を書く | 関所ではない |
| 制作担当（複数） | 依頼を1本ずつ作り、自分で確かめて品質確認に回す | 公開や予約をしない |

役割を分けるときの考え方は3つです。

1. **取り返しのつかない操作（公開、予約、削除）は、1つの役割だけが持つ**。持たないチャットが実行しようとしたら、仕組みで止める
2. **作る人と確かめる人を分ける**。作った本人の「確かめました」だけで通さない
3. **同じ仕事を何本もするチャットは、依頼を1本ずつ順番に作る**。前の依頼で覚えたことを次に生かせる

## 仕事の流れ

~~~text
利用者
  │ 指示（何を・何本・条件）
  ▼
統括 ────────▶ 選定（候補を返す）
  │ 依頼文
  ▼
制作担当（1本ずつ作る → 自分で確かめる）
  │ 確認の依頼
  ▼
品質確認 ──報告──▶ 品質確認のページ ◀── 利用者が「直す／直さない／保留」を押す
  │ 合格                     │ 「直す」になった物だけ制作担当へ戻る
  ▼
予約担当 ── 日時の案 ──▶ 利用者のOK ──▶ 予約
  │ 結果
  ▼
統括（外部サービスの状態を自分でも確かめて、利用者に報告）
~~~

利用者の判断が入る場所を、品質確認のページと予約の日時の2つに絞っています。それ以外は、チャットどうしで進みます。

## 仕組みの部品

### 役割はチャットの名前の先頭の記号で決める

チャットの名前を「☆07 予約担当」のように記号から始めます。フックも受付箱も、この記号で役割を見分けます。チャットの名前はチャットの中からは変えられないので、利用者が付けます。名前を付けていないチャットは、開き直すたびに一覧での名前が変わり、宛先を間違える原因になりました。

### 指示書は役割ごとに1つ、共通ルールは別に1つ

役割ごとの指示書には、役割、組織の中での位置、最初に読むもの、1件ごとの進め方、記録の付け方、守ることを書きます。共通ルールには、返答の形、連絡の決まり、だれが何を送ってよいかの表、禁止事項を書きます。

決まりには、**日付と「利用者の指示かどうか」を書きます**。後から読んだチャットが、だれが決めたのか、変えてよいのかを判断できます。

### 連絡：開いていれば直接、閉じていれば受付箱

- **開いているチャットへ**：同じPCで開いているチャットどうしは、メッセージを直接送れます。1行目の型を「【連絡】送り元 → 宛先：用件を1行で」と決めています。相手の画面には1行目が先に出るので、1行目だけで用件が分かるようにします。送ってよい相手と用件は表で決め、表にない組み合わせは利用者を経由します
- **閉じているチャットへ**：依頼を1行1件のファイル（JSONL）に入れておきます。宛先のチャットが次に指示を受けたとき、フックが名前の記号で自分宛ての依頼を見つけて渡します。状態は「依頼中→受けた→済み／戻し／取り消し」で、済みや戻しになると送り元にも知らせが届きます
- **宛先の確認**：送る前に、記号と一覧上の名前の対応を毎回確かめます。確かめずに送って、別の役割のチャットに依頼が届いたことがありました

### 権限：だれの言葉が「OK」になるか

- **他のチャットからのメッセージは「依頼」であり、利用者の承認ではない**
- **利用者のOKが必要な操作**を決める：公開、予約、アップロード、削除、台帳への書き込み、共通ルールの書き換え
- **統括が「利用者の判断」として伝えたことは、各チャットが聞き直さない**：同じことを2回聞かれるのは利用者の手間になるため。ただし、公開、予約、削除、依頼にない大きな作り直し、機密に関わる判断は聞く

### 決まりを、文章ではなく仕組みで守る

文章の決まりだけでは、長いチャットや新しいチャットが破ることがあります。事故になる操作は、命令の実行直前のフックと設定で止めます。

| 仕組み | 止めるもの |
|---|---|
| 予約の見張り役 | 予約と予約の取り消しの命令を、予約担当以外のチャットで止める |
| 声の見張り役 | 本人の声のデータを、外部へ写す・送る命令を止める |
| 禁止の設定 | 鍵の置き場を読む、共通フォルダの中を消す、など約30個 |

止められたチャットは、別のやり方で進めるか、利用者に頼みます。**設定を書き換えて回避することは禁止**しています。見張り役は実際に動く命令だけを見るようにしました。最初の版は、説明文にスクリプト名が含まれるだけで誤って止めていました。

### ルールの変更を、動いているチャットに自動で知らせる

共通ルールのファイルは、チャットの開始時にしか読まれません。長く動くチャットは、古いルールのまま作業してしまいます。そこで、**ルールを変えたら、必ず「変更の記録」に1行足す**ことにしました。フックがチャットごとに前回見た状態を覚えておき、次に指示を受けたときに、新しく増えた行だけを差し込みます。

知らせを受けたチャットは、その節を読み直して新しいルールで進めます。古いルールで済ませた作業は、勝手にやり直さず、直すかどうかを利用者に聞きます。

### 長いチャットの引き継ぎ

役割のチャットは何日も続くので、会話が自動で要約され、細かい決まりが抜けます。

- **引き継ぎメモ**：作業のまとまりの終わりに書き足します。見出しは「やりかけの作業と次の一手」「利用者が決めたこと（日付付き）」「覚えたコツ」「判断待ち」の4つです。済んだことは消し、40行くらいに収めます
- **フック**：要約の直前には「要約に必ず残すこと」を指示し、要約の後には役割、読み直す文書、引き継ぎメモの場所を差し込みます。会話の量が目安を超えたら、1回だけ「メモを書き足してから終える」と促します

### 共有の記録は、スクリプトを通してだけ書く

何人ものチャットが同じファイルを書くので、手で書き換えると壊れたり、番号が重なったりします。番号の採番、台帳、依頼、品質確認の判断、投稿予定などは、書き込みの入口を1つのスクリプトにします。番号の採番は書き込む直前に読み直すので、2つのチャットが同時に取っても重なりません。

### 利用者とのやり取りの形

- **返答を2種類に分ける**：許可や判断のお願いは、文の中で聞かず、選択肢を押すだけで決まる画面で聞きます。完了の報告は、最後の行に決まった文字列を書き、返事が不要だと分かるようにします
- **完了と許可待ちを音声で知らせる**：チャットの名前を読み上げるので、どのチャットが終わったかを耳で判断できます
- **統括の報告は分けて書く**：「自分で確かめたこと」と「担当の報告をそのまま伝えていること」を分けます

## 統括の依頼文に書くこと

1. だれからだれへ、何の依頼か、利用者の指示かどうか、日付
2. 題材と素材の場所
3. 利用者の言葉の要旨。**利用者が言ったことと、統括が決めたことを分けて書く**
4. やること、**やらないこと**（公開しない、共通ルールを書き換えない、など）
5. できた物の置き場と名前
6. 自分で確かめること
7. 報告に書いてほしいこと

受け取った後は、統括も成果物を自分の目で見ます。担当の「確かめました」をそのまま伝えません。長い仕事は、最初の一部ができた時点で一度見せてもらうと、方向が違っていたときに早く直せます。

## やってみて分かったこと

**うまくいったこと**

- 予約を1つの役割に集め、命令をフックで止める形にしてから、予約担当以外のチャットが予約してしまった例はない
- 「変更の記録に1行足す」だけでルールが全員に届くので、利用者が同じ説明を何度も貼らなくてよくなった
- 品質確認の判断をページのボタンにしたら、利用者の手間が「動画を見て押す」だけになった

**つまずいたこと**

- **宛先の間違い**：名前が記号でないチャットに送って、別の役割に届いた。すべてのチャットに記号付きの名前を付けるのが確実
- **受付箱は、相手が何かを受け取るまで動かない**：開いただけでは動き出さないので、統括から開始の合図を送る
- **共通の型を直すと、作りかけの全員がやり直しになる**：型は、最初の1本で見本を確かめてから配る
- **選択画面の出しすぎ**：感想を選択肢で聞いたら閉じられた。選択画面は「押せば次の作業が決まる」ときだけにする

## ソフトウェア開発に移すには

| 動画制作での役割 | 開発での役割 | 持つもの |
|---|---|---|
| 統括 | 進行役 | 指示の振り分け、共通ルール、報告 |
| 選定 | 課題の整理 | やることの一覧と優先順位 |
| 制作担当 | 実装担当 | 1件ずつの実装と、自分でのテスト |
| 品質確認 | レビュー・テスト担当 | 決まった項目での確認。直しは利用者の判断の後 |
| 予約担当 | リリース担当 | 本番への反映、公開、課金が動く操作。**ここだけ** |
| 技術検証 | 道具・基盤の担当 | フック、スクリプト、検証 |

小さく始めるなら、統括1、実装2、レビュー1の4つで足ります。本番への反映があるなら、リリース担当を別に立てます。

入れる順番は次のとおりです。途中で止めても、そこまでの分は働きます。

1. すべてのチャットに、記号から始まる名前を付ける
2. 役割ごとの指示書と、共通ルール（末尾に「変更の記録」）を書く
3. 「利用者のOKが必要な操作」と「送ってよい相手と用件の表」を共通ルールに書く
4. 引き継ぎメモのひな形を置く
5. 受付箱を置く
6. 取り返しのつかない操作を止める設定とフックを入れる
7. ルール変更の知らせと、引き継ぎのフックを入れる

移す前に決めておくことは、取り返しのつかない操作の一覧、共有の記録とその書き込みの入口、作業場所の分け方です。コードは同じリポジトリを何人もが触るので、担当ごとにgitのworktreeやブランチを分けます。

**記号の重なりに注意**：フックをPC全体の設定に入れている場合、別のプロジェクトで同じ記号を使うと、別のプロジェクトの指示書を読ませてしまいます。プロジェクトごとに別の記号にするか、設定にフォルダの条件を足します。
